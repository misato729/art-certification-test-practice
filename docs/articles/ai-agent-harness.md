# AGENTS.mdだけに頼らず、進捗・完了判定・引き継ぎをリポジトリに持たせてみた

タグ候補: `AI` `AIエージェント` `Node.js` `開発プロセス` `ハーネスエンジニアリング`

AIと継続してWebサービスを開発していると、コード以外にも覚えておいてほしいことが増えます。

「何を依頼したか」「どこまで確認したか」「資料待ちで止まっているのか」「実装しただけなのか、本番まで反映したのか」。これらを会話だけで管理すると、セッションをまたいだときに確認が必要になります。一方、すべてをAGENTS.mdへ追記すると、恒久的なルールと一時的な進捗が混ざってしまいます。

そこで、作業中のサービスで使っていた仕組みを整理し、別の試験対策サービスにも使えるテンプレートへ移植しました。Node.jsの標準機能で動く、小さな作業支援CLIです。

以下のコマンドは独自に実装したCLIです。実装リポジトリは現時点では非公開のため、この記事では構成と判断の仕組みを紹介します。アプリはTypeScriptですが、このCLIには追加のライブラリを導入せず、Node.jsで直接実行できるJavaScriptを使いました。

設計を整理する際は、[入力・プロセス・検証を整理した記事](https://qiita.com/ko1-ino/items/ccc64ce6504c77100cfb)と、[長く続く作業の状態管理を扱った記事](https://qiita.com/miruky/items/155f3b5a0dcde72fcd10)を参考にしました。ここから先は、今回のテンプレートで採用した設計です。

## 何をどこに置くか

役割を次のように分けました。

| 置き場所 | 記録するもの |
| --- | --- |
| `AGENTS.md` | 変更範囲、検証、秘密情報などの共通ルール |
| `docs/workflow/state.json` | 現在のタスク、依存関係、受入条件、評価履歴 |
| `docs/workflow/contexts/*.md` | 文脈ごとに最初に読む短い案内 |
| `docs/workflow/handoffs/*.json` | 区切りごとの引き継ぎ記録 |
| `docs/verification.md`など | 具体的に行った検証と結果 |
| `docs/workflow/policy.json` | リポジトリへ送らない資料の配置ルール |

進捗の正本はstateです。文脈カードへ同じタスク一覧を複製したり、引き継ぎのたびに大量のログを転載したりはしません。

カードは「学習設計・サービスの方針」「実装・検証」「資料・データ・配信の運用」の3つです。読む資料と守る境界を書きます。実装のカードには、既存構成の優先、重い検査の同時実行を避けること、今回の検証と過去の記録を区別することを置きました。

画面の認識合わせが必要な場合は、小さな試作を先に確認する方針も加えました。[モックを使って要件を確認する実践記事](https://qiita.com/kazuki_ogawa/items/f1a15a199d9f91fe6080)を参考にした部分です。今回の移植で新しい画面を作ったわけではありません。

既存のNuxt / Nitro / Better Auth / Prisma / Zodの構成は維持しています。

## 最初は空の状態で配る

テンプレートには、移植元のタスクや完了履歴を入れません。

```json
{
  "schema_version": 1,
  "revision": 0,
  "updated_at": null,
  "active_context": "development",
  "last_checkpoint": null,
  "tasks": []
}
```

stateの抜粋です。実際には文脈カードや鮮度確認の対象も定義しています。

他のサービスで「公開が承認された」「このDBを移行してよい」と合意していても、新しいサービスの権限にはなりません。移植元の資料名や個人の絶対パスも持ち込みません。

タスクの書き方は`task.example.json`で示しますが、このファイルを置いただけでは登録も着手もされません。実際の依頼を受けてから、対象と条件を具体化します。

## 作業開始時は必要な情報から読む

基本の確認は次のコマンドです。

```sh
git status --short
node scripts/context.mjs status
node scripts/context.mjs start development
node scripts/context.mjs next
```

`status`は進捗と前回記録からの変化を表示します。`start`は選んだ文脈のカードを表示し、`next`は依頼済みで依存関係が解消した候補を示します。

候補が出てもコマンドは実行しません。資料待ちや未依頼の作業を勝手に進めず、独立した依頼済みの作業があれば続けるための案内です。

AGENTS、現在地、対象カード、必要な根拠の順で確認します。

## 「doneと書いたから完了」を避ける

タスクには、受入条件と実行担当、評価回数の上限を持たせます。例の一部は次の形です。

```json
{
  "authorization": "not_requested",
  "request_ref": null,
  "execution": {
    "worker": "assign_before_work",
    "max_attempts": 3,
    "attempts": []
  }
}
```

着手前に依頼の根拠を記録し、自動検査と実装担当以外のレビューを受入条件へ追加します。検査方法を書いただけで成功扱いにはせず、実施後に結果、根拠ファイル、確認日を記録します。

```sh
node scripts/context.mjs gate --task task_id
```

`gate`は条件の充足状況を判定する読取専用のコマンドです。合格は終了コード0、未達や待機は2、入力不正は1です。成功した検査も、未解決の指摘が残ったレビューも、同じ「確認済み」に丸めないようにしました。

ただし、ファイルが存在することと、その内容が正しいことは別です。この判定だけで、実際に画面を操作したことや、検査結果が正確であることまでは証明できません。実際の検証と独立レビューが必要です。

## 評価の繰り返しに上限を設ける

不合格だった場合は、原因と次の行動を評価履歴へ残します。

```sh
node scripts/context.mjs attempt --context development --task task_id \
  --outcome failed --expect-revision 0 \
  --summary '未達の受入条件と原因を検証資料に記録した' \
  --next '指摘を修正して再評価する'
```

IDや世代番号は現在の状態へ置き換えます。`max_attempts: 3`は、初回を含めて最大3回の評価です。個々のテストコマンドを何回実行したかとは区別しています。

上限に達した不合格は`needs_review`にします。履歴を消したり、上限を繰り返し増やしたりして続行せず、原因と計画を見直します。依頼や条件が変わった場合は、旧記録を残して別タスクへ分けます。

全条件を確認して`--outcome passed`を記録しても、その時点ではタスクは`doing`です。タスク全体の根拠、確認日、確認範囲をそろえてから、`checkpoint --status done`で完了を記録します。

## 依存グラフは同じデータから作る

ループやグラフの設計は、[グラフエンジニアリングの入門記事](https://qiita.com/ksonoda/items/f77ea69c0c2c7c9a4c1c)が参考になりました。今回採用したのは、上限付きの評価履歴と、タスク間の依存関係です。

タスク間の依存関係は`depends_on`へ記録します。

```sh
node scripts/context.mjs graph --format mermaid
node scripts/context.mjs graph --format json
```

MermaidとJSONのどちらも、stateの同じ情報から生成します。別の図だけが古くなるのを避けるため、グラフ用の定義は増やしていません。循環した依存関係も検査します。

## 引き継ぎには世代と変化を残す

`checkpoint`は引き継ぎ記録を追加し、stateの世代番号を進めます。過去の記録は上書きしません。

更新時はロックと世代番号を確認します。複数担当で作業するときも、stateの更新担当は1人にまとめます。古い世代のまま書き込もうとした場合は、最新状態を読み直して合流します。

記録にはGitのHEAD、変更ファイル名と状態、小さな対象ファイルのSHA-256、stateのハッシュを含めます。Git差分本文や教材本文を自動収集する仕組みにはしていません。

`check --strict`は、基準記録がない場合や記録後に変化がある場合に終了コード2を返します。そのため、空の初期状態で2が返るのは想定どおりです。ハッシュが一致しても、アプリや外部サービスを再検証したことにはなりません。

## 資料の送信防止も共通化する

サービス開発では、コードと同じ場所に置けても、リモートへ送れない資料があります。既定では`local-only/`配下をGitとDockerの対象から除外します。

```json
{
  "schema_version": 1,
  "local_only": {
    "directory_names": ["local-only"],
    "filename_prefixes": []
  }
}
```

保護対象の名前は共通モジュールで判定します。ただしpolicyの変更で`.gitignore`と`.dockerignore`が書き換わるわけではありません。配置ルールを変えたら、両方の除外設定もそろえます。

送信前の検査では、現在の追跡対象だけでなく送信される履歴のファイル名も確認します。いったんコミットした資料は、現在のファイルを削除しただけでは履歴から消えないためです。

```sh
node scripts/check-private-sources.mjs
```

本文は読みません。そのため、別名にした資料の内容まで見抜けるものではありません。名前による検査の限界は残ります。ローカルのpre-pushフックも、コピーしただけでは有効にならず、既存設定を確認して明示的に導入します。

## レビューで確認した境界

移植時の独立レビューでは、`git log --name-only`だけでは通常のマージ差分が出ない点が見つかりました。マージ時にだけ追加された保護対象ファイルを、現在のインデックスから削除すると、検査を通り抜ける余地がありました。`-m --full-history`を指定し、各親との差分と履歴を確認するよう修正しました。

もう1つは出力先です。読み込む根拠ファイルのリンク先は確認していましたが、引き継ぎ記録の保存先が外向きのシンボリックリンクだった場合の検査が不足していました。ロック作成前とファイル書込前に、保存先の実体がリポジトリ内にあるかを確認するよう修正しました。

これらを再現する回帰テストを追加し、ローカルのNode.js 22.15.1で軽量テスト162件が成功しました。失敗・スキップは0です。検査には原資料を使わず、合成データと一時Git環境を使っています。アプリ・DB・ブラウザの検査や、速度・費用の削減効果の測定は今回の確認範囲に含めていません。

CIにはNode.js 24で同じ軽量検査を行うジョブを追加しました。アプリ側の検査は、このジョブの成功後に進む構成です。ローカルの検査結果とCIの実行結果は分けて扱います。

## 使う範囲を絞る

これはタスクの整理と判断の根拠を残す仕組みです。全自動のエージェントランナーではありません。サーバー起動、DB操作、テスト、自動コミット、公開などを、進捗確認から連続して実行することはありません。

まずは短い文脈カードと空のstateから始めて、実際の依頼に必要な条件を追加する形にしました。軽い文書変更に全件ビルドを要求するような使い方は避け、変更に応じた確認を選びます。

コードだけでなく、「何を根拠に、どこまで終えたと判断したか」を次のセッションへ渡せるようにする。今回テンプレートへ持たせたかったのは、その部分です。
